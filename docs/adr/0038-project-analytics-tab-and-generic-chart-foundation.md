# ADR-0038: プロジェクト分析タブの新設 + 汎用チャート基盤 (WBS 予実カーブ)

- **Status**: Accepted
- **Date**: 2026-06-11
- **Deciders**: PM (teppei) + Claude Code
- **Related**: [ADR-0003](./0003-embedding-based-suggestion-engine.md) (提案タブの隣に配置) / SCREENS.md §11.5b / SERVICES.md (analytics.service.ts)

---

## Context (背景)

プロジェクトの PM/PL から「完了に向けて今どこまで進んでいるか（現在地）」と「どのくらいのペースで消化できているか（生産性）」を、会議・進捗報告の前に **1 枚で把握したい** という要望があった。WBS には予定/実績の日付・進捗が入力済みだが、それらを俯瞰するビューが無く、ガントチャート（日程の可視化）とも目的が異なる。

加えて、分析の対象は WBS にとどまらず、将来は課題・リスクの推移など他観点にも広げたい。そのため、特定ドメインに密結合した単発画面ではなく、**分析を継ぎ足せる共通基盤** として設計する必要があった。

## Decision (決定)

プロジェクト詳細に **「分析」タブ** を新設する（タブ並び: 「ナレッジ一覧」と「参考」の間）。パネルを縦に並べる構成とし、初期は **(1) WBS 予実カーブ**（折れ線）、**(2) 担当者別 週次消化工数**（積み上げ棒 + 工数効率）、**(3) 担当者別 予定 vs 実績 工数**（グループ棒）、**(4) 担当者別 作業負担**（未完了予定工数の状態別積み上げ棒 + 量/個人ペース補正 切替）、**(5) 担当者別 日次工数**（1 日 8h 上限チェックのヒートマップ）の 5 枚を提供する。(1) で遅れ/先行を、(2) でその「なぜ」を、(3) で見積精度を、(4) で「今 誰に作業が多く残っているか」(総量) を、(5) で「いつ 誰の負荷が 1 日 8h を超えるか」(山積み) を見て負荷分散・割り振りの参考にする。(4) は総量、(5) は日次のピークと、軸を分けて重複を避ける。

(4) の指標は person-neutral な「予定工数」が起点のため正確な負担にはならない点を踏まえ、**モード切替**を持たせた: 「割り振り量」(予定工数そのもの) と「個人ペース補正」(各担当者の実績÷予定比を掛けた予想残工数。スピード差を織り込む。履歴なしは×1)。いずれも見積誤差は残り、個人評価には使わない旨を UI/FAQ/ガイドに明記する。

### 1. 表示・認可

- 表示ロール = `systemRole==='admin'` または プロジェクト `projectRole==='pm_tl'`（member / viewer 非表示）。
- 新アクション **`analytics:read`** を権限フレームワーク（check-permission.ts）に追加。admin / pm_tl に付与。API でも `checkProjectPermission('analytics:read')` で二重防御（非該当 403 / 非メンバー 404）。
- 読み取り専用のため **closed プロジェクトでも閲覧可**（`STATE_RESTRICTIONS.closed` に `analytics:read` を追加）。完了案件の振り返り分析に有用。

### 2. WBS 予実カーブの集計仕様 (確定)

- 分母 = ACT（type='activity', 削除除く）の総数。WP は分母に含めない。
- 縦軸 = 着手割合（0〜100%、10% 刻み）。横軸 = 日次（最小予定開始日 〜 max(最大予定完了日, 最大実績完了日, 本日)）。
- **予定線（実線）**: 各日 d で「予定完了日 ≤ d」の ACT 累積件数 ÷ 総数。
- **実績線（点線）**: 各日 d で「status='completed' かつ 実績完了日 ≤ d」の ACT 累積件数 ÷ 総数。**本日より後は描かない（null）**。
- 期間が複数日にまたがる ACT も、按分せず**完了日の 1 点に丸ごと計上**。
- 本日マーカー（縦線）+「本日時点 予定◯% / 実績◯%（遅れ◯%）」サマリ。

実績線は `TaskProgressLog`（進捗履歴）ではなく Task 本体の `actualEndDate` + `status` から再構成する。これにより **既存データだけで近似なく** 描画でき、追加の入力項目も不要。

### 3. 汎用 3 層基盤

| 層 | 実体 | 責務 |
|---|---|---|
| データ | `src/services/analytics.service.ts` (`getWbsCompletionCurve`) | ドメイン数値（件数・割合）のみ返す。表示を知らない。tenantId 越境は `project: { tenantId }` で遮断 |
| 組み立て | `analysis/analysis-panels.ts` (パネルレジストリ) | API から取得した数値 + i18n を `AnalysisChart` 契約に変換（色・線種・本日参照線） |
| 描画 | `src/components/charts/time-series-chart.tsx` / `stacked-bar-chart.tsx` / `grouped-bar-chart.tsx` (`AnalysisChart` 契約) / `heatmap-table.tsx` (`AnalysisHeatmap` 契約) | Recharts 折れ線 / 積み上げ棒 / グループ棒、HTML 表ヒートマップ。ドメインを知らない |

`AnalysisChart.kind: 'line' | 'stacked-bar' | 'grouped-bar'` で描画部品を出し分ける。系列 (`AnalysisSeries`) は全形式で共有（折れ線=1本の線、積み上げ棒/グループ棒=1カテゴリ or 1比較軸）。**パネル2（消化工数）は `kind:'stacked-bar'` のパネル登録のみで追加**。パネル3（予実差）は新しい描画形式が必要だったため `kind:'grouped-bar'` + `GroupedBarChart` を 1 つ追加し、パネルを登録した（タブ・既存パネル・既存チャート部品・チャート契約の本体は無改修。契約は kind の値を 1 つ増やしただけ）。パネル4（作業負担）は既存 `kind:'stacked-bar'` を流用しつつ、**パネルに任意の `modes` (切替) を持たせる拡張**を基盤に加えた（`AnalysisPanelCard` がセグメント切替を描き `build(raw, labels, mode)` を呼ぶ）。既存パネル1-3は `modes` 無しで無改修。

**パネル5（日次工数）は折れ線/棒では表せない「行×列の色分け一覧」だったため、新契約 `AnalysisHeatmap`（`columns` / `rows[].cells[]` / `unit`）+ 描画部品 `HeatmapTable` を 1 つ追加した。** あわせて `AnalysisRenderData` を「`chart` か `heatmap` のいずれか」を持つ形に拡張し、`AnalysisPanelCard` が `heatmap` を優先して出し分ける。既存パネル1-4（`chart` のみ）は無改修。これは基盤の設計通り「新しい描画形式が要るときだけ部品を 1 つ足す」を 2 度目に実証したケース。分析の追加 = `analysis-panels.ts` にパネル 1 つを登録するだけ（切替が要るときは `modes`、新形式が要るときは契約+部品を 1 つ追加するだけ）。

担当者別 週次消化工数の集計仕様: 完了 ACT（status='completed' かつ実績完了日あり）の **実績工数 (Task.actualEffort)** を実績完了日の週（月曜始まり）× 担当者で **SUM (人時)**。横軸は最初の完了週〜max(本日週, 最後の完了週) を連続表示。実績工数の上位 8 人を個別色、残りは「その他」に集約（未割当は別グループ）。あわせて **工数効率 = Σ予定工数 ÷ Σ実績工数**（完了 + 実工数入力済の ACT のみ）をパネル要約に表示する。

**「件数」ではなく「工数」で測る理由 (2026-06-11 追補)**: 当初パネル2は「完了 ACT 件数」を積み上げていたが、ACT の粒度が不均一（1 件が 1h のことも 40h のこともある）なため、件数は「生産性」を表さない（完了イベントのスループットにすぎない）という指摘を受けた。そこで担当者が実績入力時に **実績工数 (Task.actualEffort, nullable)** を入力できるようにし（WBS 実績入力ダイアログに追加。validator/updateTask は既存に追従）、パネル2を実績工数の積み上げ + 工数効率（EVM の CPI 相当）に作り替えた。これにより「作業量（工数）」と「見積に対する効率」で生産性を読み解けるようにした。なお実工数は手入力依存で、効率は「見積に対する効率」であり絶対的生産性ではない点、個人評価 KPI 化は避けるべき点を docs/FAQ に明記している。実工数未入力の完了 ACT は棒に乗らず効率母数からも除外（入力を促す設計）。

担当者別 日次工数 (1 日 8h 上限チェック) の集計仕様 (2026-06-12 追補): 未完了 ACT（status が `not_started` / `in_progress`。完了・**保留 `on_hold` は除外**）の予定工数を、予定期間（予定開始日〜予定完了日, inclusive）の日数で **均等按分**し、担当者×日付で合算する（WBS 編集ダイアログの日次工数プレビュー `getAssigneeDailyWorkload` と同ロジックを分析サービスに移植）。横軸は **本日（テナント TZ）〜 未完了タスクの最大予定完了日**。本日より前の按分日は表示しない（過去の負荷は対象外）。各セルは日次工数を `config/workload.ts#classifyWorkloadLevel` で **≤7h=OK / >7h=警告 / >8h=超過** に分類し、ヒートマップで色分けする（WBS 編集時のオーバーアサイン警告と同じ 7h/8h 閾値を流用）。担当者は **超過日数 → 警告日数 → 最大日次工数** の降順で並べる（逼迫している人を上に）。

**パネル4 (作業負担) との役割分担**: パネル4 は「未完了の予定工数 **総量**」で誰に多く残っているかを比較する（縦棒・累計）。パネル5 は同じ未完了予定工数を **日次に展開して 1 日 8h の上限超過（山積み）** を見る（ヒートマップ・ピーク）。総量が同じでも、短期間に詰め込まれていれば 8h 超で赤くなる。両者は「量」と「いつ」で軸が直交するため重複せず、負荷分散の判断材料を補完し合う。**限界**: 均等按分は概算で実際の作業配分（前倒し/後ろ倒し）を反映せず、土日祝も 1 日として按分する（営業日按分は将来拡張）。個人評価には使わない旨を UI/FAQ/ガイドに明記。

### 3-bis. 表示グラフの選択 + 対象期間 (2026-06-12 追補)

5 パネルを全て常時縦並びにすると「全容スコープのグラフが並んで見づらい」という指摘を受け、ツールバーを追加した。

- **表示グラフの選択**: チップ (複数選択) で表示パネルを絞る。**OFF のパネルは fetch しない** (遅延)。**初期は予実カーブ 1 枚のみ** (`DEFAULT_VISIBLE`) として縦並びの圧迫を解消。
- **対象期間**: `全期間 / 直近1・3・6ヶ月 / カスタム(from–to)`。**数値も期間で再集計する**方針 (表示クリップだけにせず、効率・合計・順位も選んだ期間で計算し直す = 表示と数値が常に一致)。
- **期間の向きはパネルの性質ごとに異なる** (`rangeKind` + `resolveRanges`):

  | rangeKind | パネル | 期間の効き方 |
  |---|---|---|
  | `past` | ①予実カーブ / ②週次消化工数 / ③予実差 | `[today-Nヶ月, today]` で対象を絞る。①は横軸クリップ (累積値は維持。窓外の日も累積加算は継続)、②③はサーバ側で対象タスクを絞り効率・合計・順位を再集計 |
  | `future` | ⑤日次工数 | 起点は常に本日、`to`(=today+Nヶ月) で未来の終端を絞る。プリセットの月数を**今後側**へ適用。`to`<本日なら空。注記表示 |
  | `none` | ④作業負担 | 現在のスナップショットのため期間を反映しない。期間指定中は注記表示 |

  過去 (①②③) と未来 (⑤) で同じプリセットを逆向きに適用するのは、「直近 N ヶ月分を見たい」という意図を、振り返り系は過去側に、負荷予測系は未来側に自然に対応させるため。`none` (④) は時点スナップショットで期間がなじまないため明示的に対象外とした。

- **サーバ側フィルタ**: 各 service に optional `AnalyticsRange` を渡し、元タスクを実績完了日 (②③) / 予定按分日 (⑤) で絞って集計する。API は `?from=&to=` で受け取り `parseAnalyticsRange` が形式不正を無視。④ は range を送らない。これにより「対象期間を選ぶ」が表示だけでなく**数値の意味**を持つ (請求 invariant と同じく「表示 = 集計値」を崩さない honesty 方針)。
- **永続化**: 表示グラフ・期間は `sessionStorage` を**ユーザ ID でキー分離** (`useSessionState` 流用) して保存し、別ユーザに引き継がない ([[feedback_client_sessionstorage_user_isolation]] の方針。分析設定は非機微だがキー分離で構造的に越境を防ぐ)。

### 4. 技術選定

- チャートライブラリ = **Recharts 3.x**（React 19 peer 対応）。分析タブは `dynamic()` 遅延ロードのため初期バンドル非影響。
- 分析クライアントは SuggestionsPanel と同様に **自前 fetch**（`LazyTabContent` には乗せない）。

## Consequences (結果)

- **Pros**: PM/PL が現在地と生産性を 1 枚で把握できる。既存データのみで正確に描画。将来の分析追加コストが小さい。
- **本日の判定**: テナントのタイムゾーン（`Tenant.timezone`、既定 `Asia/Tokyo`=JST）の暦日で算出する（ガント／画面表示と同じ `getTenantTodayString` を流用）。UTC 起点で日付がずれる罠を排除。日本のテナントは JST で本日を判定する。
- **Cons / 留意**: 実績の「日々の履歴」は持たないため、過去時点での途中経過の厳密な再現はしない（完了日ベースの累積で表現）。`TaskProgressLog` を活性化すれば、より厳密な時系列実績へ拡張できる（将来）。
- **テスト**: analytics.service の集計（越境・空・WP 除外・予定/実績累積・未来 null・同一日複数・本日サマリ・100%、パネル5 は 按分・本日以降クリップ・完了/保留除外・7h/8h 閾値境界・並び順・空セル・TZ）を単体で担保。route は認可（member/viewer 403）とテナント受け渡しを担保。E2E（25-project-analytics.spec.ts）で admin/pm_tl 表示→5 パネル描画 / member 非表示を検証。
