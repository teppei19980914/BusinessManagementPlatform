# ADR-0010: プロジェクト状態マシン (7 状態 + 一方向遷移) を業務ロジックの中核に据える

- **Status**: Accepted
- **Date**: 2026-04 (MVP 設計時)
- **Deciders**: teppei

---

## Context

プロジェクト運営ツールとして、各プロジェクトの「いま何をする時期か」をシステム側が把握し、それに応じて操作を制限する必要があった。
PMBOK 等の標準的なプロジェクトライフサイクル (Initiating / Planning / Executing / Monitoring / Closing) を参考にしつつ、本サービスの差別化点である「振り返り → ナレッジ蓄積」を組み込んだ独自の状態モデルを設計する。

検討時の制約:

- **状態は業務の操作可否を決める**: 例えば「計画中」のプロジェクトでタスク実績更新を許すと業務ロジックが破綻する
- **業務担当者の認知負荷を最小化**: 状態が多すぎると現場が「いまどの段階?」を理解できない
- **状態遷移は監査可能であるべき**: 誰がいつどの状態に変えたかを `audit_logs` に記録
- **振り返りフェーズを設計に組み込む**: 完了したプロジェクトのナレッジ化 (= 提案エンジンへの貢献) を必須化したい
- **後戻り (revert) の扱い**: 完了したプロジェクトを再開できるべきか、それとも一方向遷移とすべきか

## Decision

**7 状態の一方向遷移マシン** を採用する。状態遷移時には自動 lock 条件を適用し、業務ロジックの整合性を保つ。

### 7 状態

| # | 状態 | 英名 | 意味 | 主な操作 |
|---|---|---|---|---|
| 1 | 企画中 | planning | プロジェクト概要・目的を整理中 | 概要編集、メンバー追加、過去ナレッジ参照 |
| 2 | 見積中 | estimating | 見積もりを作成中 | 見積もり項目編集、過去実績参照 |
| 3 | 計画中 | scheduling | WBS / タスクのスケジュールを確定中 | WBS 編集、担当割当 |
| 4 | 実行中 | executing | タスクが進行中 | 進捗・実績更新、リスク・課題起票、ナレッジ登録 |
| 5 | 完了 | completed | 全タスク完了、業務的に終了 | 振り返り起票への遷移、ナレッジ追加可 |
| 6 | 振り返り完了 | retrospected | 振り返り実施済、知見がナレッジ化済 | クローズへの遷移のみ |
| 7 | クローズ | closed | アーカイブ済、原則編集不可 | (read only) |

### 遷移ルール

- **一方向遷移**: `1 → 2 → 3 → 4 → 5 → 6 → 7` の順序のみ許可。**戻し (revert) は不可**
- **遷移トリガ**: PM/TL ロール (またはテナント admin) の明示操作のみ。自動遷移なし
- **遷移時の lock 条件** (詳細は [PROJECT_LIFECYCLE.md §10](../business/PROJECT_LIFECYCLE.md)):
  - 「計画中 → 実行中」遷移時に WBS が空ならエラー
  - 「実行中 → 完了」遷移時に未完了タスクがあれば警告 (許可は可)
  - 「完了 → 振り返り完了」遷移時に振り返りエンティティが必須

### 状態 × 操作の権限マトリクス

状態ごとに「許可される操作」を明示的に定義し、Service 層でチェック。
詳細は [docs/business/PROJECT_LIFECYCLE.md §9](../business/PROJECT_LIFECYCLE.md)。

## Consequences

### Positive
- **業務ロジックがシステムで担保される**: 「計画中のプロジェクトに実績入れない」等のミスを UI レベルで防げる
- **ユーザの認知負荷が低い**: 7 状態は一般的な PM 知識と整合 (企画 → 見積 → 計画 → 実行 → 振り返り は WBS の枠を超えた標準フロー)
- **監査可能性**: 状態遷移は `audit_logs` に必ず記録、後から「いつ実行中になったか」を追跡可
- **提案エンジンとの整合**: 振り返り完了したプロジェクトのナレッジは提案候補の主要ソースになり、状態が「ナレッジ化済かどうか」のフラグとして機能する
- **クローズ後の意図しない編集を防ぐ**: 過去プロジェクトの数字が後から書き換わる事故を構造的に防止

### Negative / Trade-off
- **一方向遷移の制約**: 「完了したけどタスク追加したい」等の業務ニーズに対応できない (専用の「再オープン」操作はあえて未実装)
- **状態遷移漏れ**: PM が忙しくて状態更新を怠ると、本サービス上のデータと実業務のフェーズがズレる (これは UI 上のリマインダ等で緩和)
- **見積もりフェーズ (見積中) の運用判断**: 簡易プロジェクトでは「企画中」と「見積中」の区別が曖昧。現状は判断を運用者に委ねる
- **状態遷移時の lock 条件が業務ロジックを複雑化**: テストケースが状態 × 操作 × ロールでマトリクス化されるため、テストコード行数が膨らむ

### Risk / 留意事項
- **PM ロール / TL ロールの遷移権限**: 「TL が勝手にクローズしてしまう」を防ぐため、特定の遷移 (完了 → 振り返り完了 等) は PM 専用にする等の判断が必要
- **状態の表記揺れ**: UI 文字列を `src/labels/` に集約 (memory: feedback_no_hardcoding)
- **enum 値の不変性**: DB の `project_status` enum の値は変更困難 (migration 必要)。新規追加・既存リネームは慎重に

## Alternatives Considered

### Alt-1: PMBOK 5 フェーズそのまま
- 概要: Initiating / Planning / Executing / Monitoring & Controlling / Closing の 5 状態
- メリット: 業界標準に完全準拠
- 不採用理由: (1) 本サービスの差別化点である「振り返り → ナレッジ蓄積」フェーズが入らない (2) Executing と Monitoring の境界が運用上曖昧 (3) 日本の現場には「企画 / 見積 / 計画 / 実行 / 振り返り」の方が直感的

### Alt-2: シンプルな 3 状態 (未着手 / 進行中 / 完了)
- 概要: GitHub Issue のような単純なライフサイクル
- メリット: 学習コスト最小
- 不採用理由: (1) 「見積もり」「振り返り」が独立フェーズとして可視化されず業務的に弱い (2) 本サービスは「企画段階で過去ナレッジを参照」が価値の核心、企画フェーズの独立性が必須

### Alt-3: 双方向遷移 (revert 許可)
- 概要: 任意の状態に戻せる柔軟なモデル
- メリット: ユーザの自由度高
- 不採用理由: (1) 「完了したプロジェクトを再開」が頻発するとデータ整合性が困難 (実績数値の上書き等) (2) 業務的には「完了 → 振り返り完了 → クローズ」が標準フローで、戻る運用は例外的。例外を許すと運用ルールが揺らぐ

### Alt-4: 状態と並行して「サブフェーズ」を持つ
- 概要: 各状態の中に詳細なサブ段階 (例: 実行中-開始 / 実行中-中盤 / 実行中-終盤)
- メリット: より詳細な進捗管理
- 不採用理由: 状態数が爆発し、UI / 権限マトリクス / テストが複雑化。進捗は別の「進捗率 %」で表現すれば十分
