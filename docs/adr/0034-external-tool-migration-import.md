# ADR-0034: 外部PMツールからの初回データ移行インポート (手動CSV + API連携 / 新規作成のみ)

- **Status**: Proposed (草案)
- **Date**: 2026-06-04
- **Deciders**: PM (teppei) + Claude Code
- **関連**: [ADR-0033](./0033-starter-data-import-and-single-tenant-suggestion.md) (スターターデータ取込=内部サンプル複製、本ADRとは別機能) / [ADR-0032](./0032-task-name-uniqueness-removal-and-wbs-import-batching.md) (WBS 名称一意性撤廃 + sync-import バッチ化、本ADRが流用) / 既存 `external-data-import.service.ts` (CSV→Knowledge/RiskIssue、本ADRが拡張)

---

## Context (背景)

LP からたすきばに辿り着いたテナント管理者にとって、**払い出し直後の最初のヤマが「既存データの移行」**である。多くの見込み顧客は Notion / Backlog / kintone / Pleasanter / Excel 等で案件・WBS・課題を管理しており、「乗り換えてもデータを持ち込めるか」が採用判断の基準になる。

現状の移行手段は、ユーザが (1) テナント設定からテンプレCSVをエクスポートし、(2) 自分でCSVに転記し、(3) インポートする、という**全工程が手作業**で負荷が高い。特に (2) の手入力が最大の障壁。

本ADRは「リリース後最初の機能」として、この移行をほぼ自動化する。手動CSVに加え、**対象サービスのAPIから対象ユーザのデータを自動取得して取り込む「API連携」**を提供する。

### 既存の取り込み機能との位置づけ

たすきばには既に複数の取り込み経路があり、本機能はそれらと役割が異なる。

| 経路 | 役割 | 本ADRとの関係 |
|---|---|---|
| `external-data-import.service.ts` | CSV → Knowledge / RiskIssue (テナント級)、preview→apply 2段階 | **本ADRが全6エンティティ + 依存解決 + API連携へ拡張** |
| `sample-clone.service.ts` (ADR-0033) | 管理テナントの**内部サンプル**を複製 (デモ体験用) | 別機能 (内部複製 vs 外部実データ移行)。UIは隣接セクション |
| `task-sync-import.service.ts` (ADR-0032) | WBS の CSV 上書き (sync-by-ID、per-project) | **本ADRが CREATE パスを流用** |
| `data-import.service.ts` (P-D) | 自社エクスポートZIPの復元 (テナント間移行/バックアップ) | 別機能 |

### 制約

- **人間駆動開発への移行 (2026-06-01〜)**: 大規模機能は段階分割し、各判断はユーザ承認を経る。
- **課金 invariant**: embedding 課金は ApiCallLog SUM = 画面表示 = 請求の一致を崩さない。
- **テナント越境防止**: 取り込みは実行管理者の自テナントに限定。
- **Netlify 関数 10 秒上限 / PgBouncer transaction mode**: 大量取込は ADR-0032 のバッチ化方針に従う。
- **各外部サービスのAPI仕様は未調査**: 階層・項目の取り出し方はサービスごとに異なり、公式ドキュメントでの実在確認が前提 (本ADR時点では未確定)。

## Decision (採用した決定)

### 1. 位置づけ = 「初回移行専用・新規作成のみ」

- 本インポートは**常に新規作成**する。既存データの更新・重複検知・スキップは**行わない**。更新したい場合は各「○○一覧」画面から行う。
- 重複制御の複雑性 (外部ID対応表・自然キー照合) は**持たない**。意図的な重複は許容 (DB容量従量課金で回収可能、初回移行前提)。
- ただし**事故的な二重送信**(確定ボタン連打・通信リトライで全件が二重作成) だけは防ぐ。既存の「apply時にpreviewを即削除」する冪等性 + ボタンdisable で対応 (= 重複判定ロジックではない)。
- この性格を**ユーザに明示**する (画面注意書き + FAQ/ガイド/たすきフクロウ)。

### 2. 対象エンティティと依存解決

- 対象6エンティティ: **顧客 / プロジェクト / WBS / リスク・課題 / ナレッジ / 振り返り**。
- 依存ルール (たすきばの作成制約に従う):
  - プロジェクト取込 → **顧客が必須**
  - WBS取込 → **プロジェクトが必須**
  - 各資産 (リスク・課題・ナレッジ・振り返り) → プロジェクト紐づけは**任意**
- **自己完結バッチ**: 取り込みは「取り込むデータの中だけ」で組み立てる (既存データは参照しない)。親も同じバッチに含める。
  - トポロジカル順 (顧客→プロジェクト→WBS/各資産) で処理。親の新規IDをバッチ内マップで子に渡す。
  - 必須の親が同バッチに無い → その行は**エラー** (一覧表示)。黙って既定テナント/空に落とさない。
  - 任意の親 (各資産のプロジェクト) が無い → 紐づけなしで取り込み (エラーにしない)。

### 3. 対象項目 = 「画面で設定できる項目のみ」

- インポート対象は**新規作成画面で設定できる項目に限定**する (DB定義より少ない。`docs/design/COLUMN_USAGE_MAP.md` / `docs/public/field-reference.md` が正本)。
- 非表示・編集専用・自動算出の項目は**対象外**: リスク/課題の「結果」(編集専用)・「優先度」(自動算出)、WBSの「優先度」「分類」(非表示、分類はシステム既定`other`補完)、ナレッジ7項目・振り返り5項目 (UI撤去/未実装) 等。
- ブランク時の扱いは2パターン:
  - **A群 (顧客・プロジェクト・WBS)**: 名称等が**ハード必須**。空はマッピングの「既定値」で補完、未設定ならプレビューでエラー。
  - **B群 (リスク・課題・ナレッジ・振り返り)**: **公開範囲**で必須が切替。**下書きならほぼ全項目が空でOK** (DBは `''` で満たす)。公開時のみ件名/タイトル/実施日が必須。
- **不可視データの防止 (2026-06-05)**: B群を**プロジェクト未紐づけ (プロジェクト名が空 or 既存・取り込み対象のどれにも不一致) かつ 公開範囲=下書き**で取り込むと、どの画面からも参照できない孤立データになる (横断「全○○」一覧は `visibility='public'` のみ表示、プロジェクト個別一覧は紐づけ必須。下書きは embedding も生成されず検索にも出ない)。よって**この組合せはプレビューでエラー化**し、プロジェクト名の指定 or 公開範囲を「公開」へ変更を促す (= 「取り込める=画面で見られる」を保証)。※公開なら未紐づけでも横断一覧に出るため許容。

### 4. 選択項目の値マッピングと不正値ルール

- 選択肢の表示値↔内部値は `src/config/master-data.ts` を**単一の正本**とする (公開範囲/プロジェクトステータス/開発方式/契約形態/影響度・重要度/発生可能性・緊急度/脅威・好機/ナレッジ種別/リスク課題の種別)。
- **空欄 → その項目の既定値**で取り込む (マッピング画面の「既定値」で補完可能。特に**公開範囲の空欄は `draft` (下書き)**)。
- **非空かつ選択肢外の値 → プレビューでエラー (取り込み不可)** ── 全プルダウン項目で統一 (2026-06-05 改訂)。
  - 当初は「不正値も既定値へ寄せて止めない」方針だったが、誤入力が黙って既定値化されると気付けない (例: 影響度に "とても高い" → 黙って `medium`) ため、**A群(プロジェクト)と同じく非空・選択肢外はエラー化**する。マッピングの「既定値」が有効ならそれを採用しエラーにしない (= 救済経路は維持)。
  - 検証は CSV パース段階 (`csv-to-batch.ts`) で `valueErrors` に集約し、プレビューで errors に合流。`value-mapping.ts` の `isKnown*` 判定 (空 or 既知値のみ真) を A群/B群で共通利用。
- **リスク/課題の `影響度`(リスク)・`重要度`(課題)、`発生可能性`(リスク)・`緊急度`(課題) は別カラム**に分離 (2026-06-05)。DB 列は `impact` / `likelihood` 単一だが、テンプレCSVでは種別ごとのラベルで列を分け、**種別に応じて使う列を切り替える** (リスク行=影響度/発生可能性、課題行=重要度/緊急度)。種別が空欄なら「課題」扱い。
- **公開時必須を満たせない行 → 公開範囲を `draft` に落として作成** (エラーで止めない)。= 「誤ったデータはすべて下書きで作成」(空欄の扱いは従来どおり。選択肢外の値のみエラー)。

### 5. 日付の正規化と厳格チェック

- たすきば所定フォーマットは **`YYYY-MM-DD`** (全バリデータが `^\d{4}-\d{2}-\d{2}$` で統一)。
- **手動CSV経路は `YYYY-MM-DD` と `YYYY/MM/DD` (Excel 既定) の両方を受理し `YYYY-MM-DD` へ正規化** ── 全日付項目で統一 (プロジェクト開始/終了、WBS開始/終了、リスク課題の期限、振り返りの実施日。2026-06-05 改訂)。
  - 当初は「`YYYY-MM-DD` 以外はエラー」と厳格化したが、**Excel で日付セルを CSV 保存すると既定でスラッシュ区切り (`YYYY/MM/DD`) になる**ため、設定変更なしでは取り込めずストレスが大きい。多くの SaaS のエクスポートも `YYYY/MM/DD` が一般的。よって `normalizeDate` を用いて**年が先頭の一般的な書式 (`-` / `/` / `.` / 空白区切り・`YYYY年M月D日`・ISO 日時・`YYYYMMDD`) を受理**し `YYYY-MM-DD` に正規化する。
  - ただし**月日が先頭の曖昧な書式 (`06/01/2026` 等) と実在しない日付 (`2026-02-30` 等) はエラー** (誤データ検知は維持)。表示・保存・アプリ内入力欄の正本は従来どおり `YYYY-MM-DD` で不変。
- **振り返りの実施日が空 → 当日を自動補完** (既存 `todayDateString` と同じ挙動)。任意日付の空欄は許容。

### 6. 担当者はブランク

- 担当者はソースのユーザをたすきばアカウントに照合する必要があり初回移行では揃わないため、**取り込まない (ブランク)**。後から各画面で割当。
- WBSのACTは作成ダイアログでは担当者必須だが、**寛容な `applySyncImport` CREATE パス**は担当者null・工数0で作成できるため、インポートはそちらを再現する (DB上 assigneeId は nullable)。

### 7. WBS階層の変換と create-only

- ソースの階層を「**前順序 (親が子より先) + 深さ (レベル)**」の共通中間形式に正規化し、既存の親スタックロジックに流す。
- **WP/ACT判定 = 構造ベース**: 子を持つ枝→`work_package`、子を持たない葉→`activity` (ソースの種別は使わない)。これにより「ACTはWP配下」制約が自動的に満たされる。
- **create-onlyアダプタ = 既存 `applySyncImport` の CREATE パス流用** (ADR-0032でバッチ化済: level昇順 `createMany` + `recalculateAllProjectWps`)。sync-by-ID更新・OCC・削除候補・更新ロールバックは使わない。projectId はバッチ内で作成したプロジェクトの新IDを渡す。
- **同名兄弟は許容** (ADR-0032 で名称一意性は撤廃済)。エラーにしない。プレビューで注意喚起の警告を出すのみ。
- 件数上限は既存値を踏襲 (DoS安全弁 `TASK_SYNC_IMPORT_MAX_ROWS`=2000、警告 300)。
- 親タスクが持つ実績 (期日/工数/担当) は、たすきばWPが集計ノードで保持できないため扱いを要設計 (推奨: 警告して捨てる)。サービス別の階層・項目の取り出し方と併せて項目9で確定。

### 8. 取り込みモード = 手動CSV + API連携、マッピングUI

- 2モード: **手動CSV** (相手ツールからエクスポートしたCSV) と **API連携** (相手APIから自動取得)。
- マッピングは**手動** (自動推定は作らない。たすきばは項目数が少なく手動で足りる)。各たすきば項目に対し **「列を割当 / 固定値を入れる / 取り込まない」の3択**。
  - カラムが多い (余る): 割り当てなければ捨てる。**複数の相手列を1項目に連結**も可。
  - カラムが少ない (足りない): 任意項目は空、必須項目は**既定値テキスト**で補完。
- ウィザード順序: **ソース選択 → (API時)認証 → データ取得 → マッピング → プレビュー+承認 → 確定 → 結果一覧**。

### 9. APIコネクタ = 汎用基盤、認証情報は即破棄

- 認証→取得→正規化を**汎用の外部サービス連携部品**として切り出し、インポート以外の将来機能でも再利用可能にする。
- 認証情報は**取得の数秒だけメモリ保持し、取得直後に破棄** (永続保存しない / OAuthはrevoke)。確定 (apply) は保存済みプレビューから実行するため認証情報を要しない。
- 認証方式はサービス別に手軽な方を第一導線 (Notion/Google=OAuth、Backlog/kintone/Pleasanter=トークン)。スコープは読み取り専用。
- 第1弾5サービス: **Notion / Backlog / kintone / Pleasanter / Excel・スプレッドシート**。各サービスの階層・項目の取り出し方は**公式API仕様の調査が前提** (本ADR時点では未確定。素直なBacklog等から順次)。

### 10. 基盤の流用と課金

- 既存 `external-data-import.service.ts` の **preview→apply 2段階フロー・課金ゲート・`tenantImportPreview` 保存 (TTL 24h)・apply時preview削除の冪等性**を多エンティティ対応へ拡張。
- コスト見積りを6エンティティに拡張 (embedding対象 = リスク・ナレッジ・振り返り)。課金 invariant (ApiCallLog SUM = 表示 = 請求) を維持。見積りはユーザ承認を経て確定。
- 結果は**1枚の一覧表** (作成 / エラー) で俯瞰表示。帯バナーは出さない。

## Consequences (影響)

### Positive

- 乗り換えの最大障壁 (CSV手入力) が解消し、API連携で対象ユーザのデータを自動取り込みできる。
- 「新規作成のみ・重複制御なし」と割り切ることで、外部ID対応表・自然キー照合・スキップ表示の複雑性をまるごと排除できる (実装・テスト面積の大幅削減)。
- 既存の preview/apply・課金ゲート・WBSバッチ化 (ADR-0032)・`createCustomer`/`createProject` を流用でき、新規はコネクタ層・依存解決・マッピングUIに集中できる。
- 汎用コネクタ基盤は将来の他連携機能でも再利用できる。

### Negative / Trade-off

- 意図的に2回取り込むと重複が量産される (許容。ユーザに位置づけを明示して納得を得る)。
- 「画面で設定できる項目のみ」対象のため、UI非表示のDB項目 (ナレッジ7・振り返り5等) は移行できない (= UI⇔DBドリフトの別論点に依存。`COLUMN_USAGE_MAP.md` Part E)。
- 担当者を取り込まないため、移行後に担当割当の手作業が残る。

### Risk / 留意事項

- **各サービスのAPI仕様は未確定**: 階層概念・項目名・ページング・レート制限・認証はサービスごとに大きく異なる。公式ドキュメントで実在確認してから実装する (ハルシネーション厳禁)。フィールド名を推測で確定しない。
- **大量取込の完走**: WBSは ADR-0032 のバッチ化で2000行まで想定。他エンティティのバッチ取込も同様に往復削減し、10秒枠を意識する。
- **schema.prisma:796 のコメントが古い**: WBS名称一意性のコメントが ADR-0032 の撤廃を反映していない (別途修正対象。本機能の判断は撤廃後の実態に従う)。
- **ADR-0033 との UI 共存**: テナント設定の「スターターデータ取込」(内部サンプル) と本機能 (外部移行) を明確に区別して並置する。

## Alternatives Considered (検討した代替案)

### Alt-1: 重複検知 + スキップ (外部ID対応表 / 自然キー照合)

- 概要: 取り込み済みを外部IDや「親+名前」で照合し、再取込時にスキップする。
- 不採用理由: 本機能は「乗り換え=初回移行」が前提で更新機能を持たない。重複が出ても運営上問題なく (従量課金)、検知ロジックは複雑性に見合わない。`ImportSourceLink` テーブル等のスキーマ追加も不要にできる。

### Alt-2: 自動マッピング推定

- 概要: 相手の列名とたすきば項目を名前類似で自動対応づける。
- 不採用理由: たすきばは項目数が少なく手動マッピングで十分。実装コストに見合わない。

### Alt-3: 既存データを参照した親解決 (バッチ外の顧客/プロジェクトに紐づけ)

- 概要: 取り込み中の親が既にたすきばに存在すれば名前照合で紐づける。
- 不採用理由: 自己完結バッチに比べ挙動が複雑化し、重複許容方針とも整合しづらい。初回移行では親も同梱するのが自然。

### Alt-4: WBS同名兄弟をプレビューでブロック

- 概要: 同一WP配下の同名タスクをエラーにする。
- 不採用理由: **ADR-0032 で名称一意性は既に撤廃済** (週内反復タスク等の正当な同名を許容)。本機能でブロックすると ADR-0032 に逆行する。警告のみとする。
