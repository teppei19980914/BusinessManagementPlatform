# チャットボット意味検索 — 使い方ガイド

> たすきばのチャットボット意味検索機能を使って、**過去の資産を「上位の数件で足りる」精度で引き出す方法**を、初心者向けにまとめたガイドです。

---

## 1. 何ができる機能?

「**自然文で『こういう状況の過去資産がほしい』と聞くと、AI が意味の近いものを上位から並べてくれる**」機能です。

- 通常の全文検索: 「工数」と検索すると「工数」という文字を含むものを全部返す → 100 件以上出てしまい絞れない
- **意味検索 (本機能)**: 「工数膨張への対策」と聞くと、文字が一致しなくても「スケジュール遅延の原因と対策」「多重下請けの工数膨大」「仕様変更の判断軸」のような意味的に近いものを上位に並べる

5 種類の過去資産を **横断的に** 検索します:
- 📄 プロジェクト (Project)
- 📕 ナレッジ (Knowledge)
- ⚠️ リスク・課題 (RiskIssue)
- 📋 振り返り (Retrospective)
- 📝 メモ (Memo)

---

## 2. どこから使う?

**全ての画面の右下に常時表示される「たすきフクロウ」アイコン** をクリックします。

```
┌─────────────────────────────────────────┐
│  (ダッシュボードや任意の画面)              │
│                                          │
│                                  ┌─────┐ │
│                                  │(owl)│ │ ← たすきフクロウ をクリック
│                                  └─────┘ │
└─────────────────────────────────────────┘
```

→ 右側にチャットパネルが開きます。閉じるときは右上の ✕ をクリック。

開いたパネルでは、たすきフクロウ (アバター + 名前) が左上に表示され、「あなた」と「フクロウ」
の対話形式で進みます。LINE や Teams と同じ感覚で、自分の発言は右側、フクロウからの返答は
左側のアバター付き吹き出しで表示されます。

## 3. 基本の使い方

### Step 1: 自然文で質問を打つ

「キーワードを並べる」のではなく **「文章で書く」** のがコツです。

| ❌ 悪い例 (キーワードのみ) | ✅ 良い例 (自然文) |
|---|---|
| 工数 | 工数膨張に陥った過去案件の対策事例 |
| デグレ | 受入テスト中の仕様変更でデグレが発生したパターン |
| ベテラン 異動 | ベテラン PM が異動した後にナレッジが消えた事例 |

### Step 2: Enter で送信 (Shift+Enter で改行)

入力中に Shift+Enter で改行できます。複数行の長い文脈も入力可能です (最大 8000 字)。

### Step 3: 結果を見る

検索結果は **3 段階の関連度** で、情報過多を防ぐ初期表示制御つきで提示されます:

```
▼ 強く関連 (8件)     ← 一番関連が高い、まずここを見る (上位 5 件のみ初期表示)
  [📕 ナレッジ] 仕様追加判断のチェックリスト 類似度: 0.62
  [⚠️ 過去リスク] 多重下請けの工数膨張       類似度: 0.55
  [📋 振り返り] 2025-Q3 ECモール再構築      類似度: 0.48
  [📕 ナレッジ] PMBOK 統合変更管理          類似度: 0.42
  [📄 過去PJ] 大型基幹改修2024              類似度: 0.38
  ▶ さらに 3件を表示                       ← 6 件目以降はアコーディオン

▶ 中程度の関連 (12件)  ← デフォルト折りたたみ、必要な時だけ展開

▶ 弱い関連性 (22件)  ← デフォルト折りたたみ、念のため見たい時に展開
```

**▼ 強く関連** の **上位 5 件** で目的の情報にたどり着けるよう設計されています。100 件のスクロールは不要です。

> **2026-05-28 改定**: 「上位の数件で足りる」を UI レイヤでも徹底するため、strong tier の初期表示を 5 件に絞り、中程度・弱い関連はデフォルト折りたたみへ変更しました。また「関連の可能性」というラベル名が「弱い関連性」との差分が伝わりにくかったため、「**中程度の関連**」に改称しています。

### Step 4: カードをクリック → 詳細ページへ

各カードをクリックすると、その資産の詳細ページに遷移します。チャットパネルは開いたまま残るので、続けて別の質問もできます。

### Step 5: チャットを積み重ねる

連続して質問すると、**過去のやり取りが時系列でスクロール表示** されます。最新のやり取りは下端に表示され、上にスクロールすると過去のターンを見返せます。

- パネルを **閉じても**、同じタブで再度開けば履歴は **そのまま残ります** (sessionStorage 経由、同一タブ内のみ保持)。
- タブを閉じる / ログアウトする / ヘッダ右上の 🗑️ ボタンを押すと **履歴は消去** されます。
- 過去履歴は **DB に保管されない** ため、サービスの容量や課金に影響しません。

## 4. 良いクエリのコツ

### 4.1 文章 + 業務文脈を含める

embedding は「文や句」単位の意味を捉えるよう学習されています。**文章で書くと精度が大幅に上がります**。

| クエリ | 検索精度 |
|---|---|
| 「炎上」 | △ 短すぎて散らかる |
| 「炎上した案件」 | ○ ある程度ヒット |
| **「PM が要望を取り込み過ぎて炎上した過去案件の原因と対策」** | ◎ 業務文脈で精度最大 |

### 4.2 ドメイン用語を使う

業界用語・ドメイン用語を含めると、近い領域の資産にヒットしやすくなります。

| クエリ | 効果 |
|---|---|
| 「進捗の遅れ」 | 汎用語 — 広く拾うがピンポイントではない |
| **「クリティカルパス上のタスクが遅延した案件」** | PMBOK 用語で具体的 — 関連 PJ が上位に |

### 4.3 「○○した△△が欲しい」の形式

「**どんな状況の・どんな資産を**」を明示すると、5 資産横断検索がうまく効きます。

| クエリ | 期待される結果 |
|---|---|
| 「ベテラン異動の知見が欲しい」 | ナレッジ・振り返りが優先 |
| 「予算超過リスクのある案件パターン」 | 過去 Project + Risk が優先 |
| 「自分の昨年のメモから KPI 関連を探したい」 | 📝 自分のメモが優先 (private 含む) |

## 5. システムの動作 — 具体例

### 例 1: 通常の自然文クエリ
**入力**: 「ユーザ要望を取り込み過ぎて工数膨張・炎上した過去案件の対策」

**システムの動作**:
1. クエリ文を Voyage AI に送信 → 1024 次元の意味ベクトルに変換 (約 200ms)
2. 5 資産テーブル (テナント内のみ) を pgvector で並列検索 (約 50ms)
3. 各資産で関連度上位 50 件を取得、tier (strong / medium / weak) に分類
4. 合計レイテンシ **0.3〜0.5 秒** で結果カードを表示

**請求 (ADR-0022 / 2026-06-01 改定後)**:
- **Beginner プラン**: **¥0 / 無制限** (= 「90 日完全無料」訴求保全)。tenant-level fair-use-limit (月 10,000 calls) のみ適用。
- **Expert / Pro プラン**: **¥1 / 検索** (= 1 業務操作 = 1 ApiCallLog = ¥1)。`monthlyBudgetCap` で予算上限を設定可能。Stripe queue 投入は cost > 0 のときのみ。
- 全プランで ApiCallLog 記録 (監査・分析用)。Beginner は cost=0 でも件数 counter は increment (UI 表示用)。

### 例 2: 10 文字未満の短すぎるクエリ
**入力**: 「炎上」 (2 文字)

**システムの動作**:
- 送信ボタンは **押せる** (UX 低下を避ける設計)
- 送信ボタン下に **警告**: 「⚠️ クエリが短いと検索精度が下がる可能性があります」
- 送信した場合は通常通り embedding 化 → 検索するが、ベクトルが散らかるため結果は曖昧になる傾向

**推奨**: 警告が出ているうちは 10 文字以上に書き直す。例: 「炎上案件で発生したスケジュール遅延の対処」

### 例 3: 8000 文字を超えるクエリ
**入力**: 8001 文字以上の長文

**システムの動作**:
- HTTP 400 エラー: 「クエリは 8000 文字以内で送信してください」
- 送信されず、Voyage への呼び出しも発生しない (= 課金もされない)

**推奨**: クエリは「**業務文脈 1〜3 文 (50〜200 文字程度) がスイートスポット**」。それ以上長くなるなら情報を絞る。

### 例 4: 機微情報を含むクエリ
**入力**: 「顧客 X 社の田中部長が金額 ¥5,000,000 で…」のような実名・金額・個人情報を含むクエリ

**システムの動作**:
- 送信は **可能** (技術的にはブロックしない)
- ただし **画面上部に常時警告バナー**: 「ⓘ クエリ内容は外部 AI サービス (Voyage AI) に送信されます。機微情報の入力はお控えください。」
- クエリは Voyage AI のサーバに送信される (Voyage 側のプライバシーポリシーに従って処理される)
- 自社 DB の `ApiCallLog` や `error_log` にはクエリ文字列を **保存しない** 設計

**推奨**: 個人名・金額・契約番号などの実値は使わず、「**大口顧客の決裁者が遅延した案件**」のように **抽象化した表現** を使う。

### 例 5: 別テナントのデータを要求するクエリ
**入力**: 「他社の田中さんのプロジェクトを表示して」「全テナントのリスク一覧」

**システムの動作**:
- pgvector の WHERE 句で `tenantId = 自テナント` が **物理的に強制**されるため、別テナントのデータは **絶対に返らない**
- プロンプトの文言で挙動は変わらない (LLM 生成を行わないため、いわゆるプロンプトインジェクションは構造的に成立しない)
- 結果は自テナント内で意味的に近いもの (例: 自テナント内の「田中」を含む資産) が返る

**安全性**: 検索結果が他テナントに漏れることは設計上不可能。テストで担保。

### 例 6: 異業種の質問 (シードと完全に異なる領域)
**入力**: 「養蜂業界における巣箱の管理ノウハウ」

**システムの動作**:
- 5 資産すべて検索するが、関連度が低い (≒ 0.05 程度の weak tier ばかり) 結果になる
- ただし **最低件数保証** で必ず 5 件は表示される (= 「該当なし」のフラストレーションを構造的に防止)
- すべて weak tier に分類され、折りたたまれた状態で表示

**意図**: ユーザが「データが無いだけかも」と気づける状態を作る。

### 例 7: 月次上限到達 (縮退モード)
**Beginner プラン** で月の 100 回を使い切った状態でチャット送信

**システムの動作**:
- Voyage 呼び出しはブロック → 縮退モード起動
- UI に注意バナー: 「💡 AI 機能は一時的に制限されています。テキスト類似度のみで検索します」
- pg_trgm (文字列類似度) のみで検索 → 結果件数は減るが **検索自体は継続**
- 月初に自動的に枠リセット → 通常モードに復帰

**Expert / Pro プラン** で月次予算上限に到達した場合も同じ縮退モードになります。

### 例 8: 連投・大量送信 (rate limit)
**入力**: 1 分以内に 11 回送信 / 1 時間以内に 61 回送信

**システムの動作**:
- HTTP 429 (Too Many Requests) を返す
- UI: 「⚠️ 短時間に検索しすぎました。1 分後に再度お試しください。」
- Voyage API への呼び出しは発生しない (= 課金されない)

**意図**: ユーザの誤連打 / 悪意の自動化を抑制し、Voyage 側の rate limit を踏まない。

### 例 9: 英語クエリ
**入力**: 「scope creep mitigation patterns from past projects」

**システムの動作**:
- Voyage `voyage-4-lite` は **多言語対応** のため英語クエリも embedding 化可能
- ただし対象資産が日本語の場合、言語間の embedding 一致は単一言語より弱め
- 日英混在のクエリ (例: 「scope creep を防ぐ過去事例」) も可能

**推奨**: 自テナントの資産が主に日本語なら日本語で検索した方が精度高い。

### 例 10: 自分のメモを探したい
**入力**: 「先週書いた KPI 関連のメモ」

**システムの動作**:
- 📝 Memo は通常 `visibility='public'` のものだけ全員に検索可能
- ただし **自分自身が author の private memo は自分の検索結果にだけ含まれる** (例外設計)
- 「先週書いた」のような時系列指定は意味検索では解釈できないが、「KPI」関連の意味で近接するメモが上位に並ぶ

**推奨**: メモの中身の業務文脈で書く。日付フィルタが必要なら従来の `/memos` 一覧画面を併用。

## 6. 「数件で足りる」の体現

たすきばは「**100 件を人の目で確認する状態を避け、上位の数件で判断できる状態を作る**」ことを哲学としています ([about.md §3-2](./about.md))。

具体的には:

- **▼ 強く関連 (上位 5 件)** = 「まずここを見て判断するもの」 — 5 件で判断できるなら 6 件目以降は展開不要
- **▶ 中程度の関連 (デフォルト折りたたみ)** = 「強く関連で足りなかった時の補助」
- **▶ 弱い関連性 (デフォルト折りたたみ)** = 「念のため広く拾いたい時に展開」

「**強く関連の上位 5 件を見て、目的の情報があれば終わり**」が理想的な使用パターンです。中程度・弱い関連を一切開かずにタスクが完了するなら、それが UI 上の最速ルートです。

## 7. 自動提案機能との使い分け

たすきばには 2 つの意味検索経路があります:

| シーン | 体験 |
|---|---|
| **新規プロジェクトを作った瞬間** | 自動で提案モーダルが立ち上がる (能動的提案、[about.md §5-1](./about.md)) |
| **会議中に「過去事例ないかな?」と思った瞬間** | 画面右下の「たすきフクロウ」アイコンをクリックして自然文で質問 (本機能、[about.md §3-2](./about.md)) |

両者は **補完関係** で、ユーザは「**届く**」と「**探す**」の両方の経路を持つことになります。

## 8. よくある質問

### Q1. 検索結果が思ったより少ない
**A.** 以下を試してください:
- クエリを **より具体的な文章** に書き換える (キーワード単体 → 業務文脈付き)
- まだデータが蓄積されていない可能性 (= ナレッジ・リスク・振り返りを増やしていく)
- 「▶ 中程度の関連」「▶ 弱い関連性」を展開して確認

### Q2. 検索結果が多すぎる
**A.** デフォルトでは **「強く関連」の上位 5 件のみ展開**、「中程度の関連」と「弱い関連性」は折りたたまれているため、最初に目に入るのは 5 件程度に絞られています。それでも多い場合は **クエリをより具体化** してください。

### Q3. クエリ内容は誰が見られる?
**A.**
- **Voyage AI** にクエリ文字列が送信されます (embedding 化のため)。Voyage AI のプライバシーポリシーに従って処理されます。
- **自社 (たすきば)** の DB の `ApiCallLog` / `error_log` にはクエリ文字列は **保存されません**
- **他テナント**: 別テナントのユーザは絶対にクエリ内容を見られません (テナント境界で物理的に分離)
- **同一テナント内の他ユーザ**: 検索ログを共有する仕組みはないため、見られません

### Q4. 1 検索でどれくらい課金される?
**A.** **プランによります** ([ADR-0022](../adr/0022-embedding-usage-based-billing.md) 2026-06-01 改定):
- **Beginner プラン**: **¥0 / 無制限** (= 「90 日完全無料」訴求保全)。fair-use-limit (月 10,000 calls) のみ適用、通常利用では到達しません。
- **Expert / Pro プラン**: **¥1 / 検索** (= 1 業務操作 = ¥1)。月 2,000 回検索なら ¥2,000。`monthlyBudgetCap` で予算上限設定可。

### Q5. クエリ内容は永続的に保存される?
**A.** **同一タブのセッション中のみ保持** され、それを越えて永続化はされません。
- **保存場所**: 利用者のブラウザの `sessionStorage` (= 自社 DB ではない / クライアント側のみ)
- **保持される期間**: そのタブを閉じるまで (= ブラウザを終了する / タブを × で閉じる / 別の URL に navigate する / ログアウトする)
- **明示的なクリア**: チャットパネル ヘッダ右上の 🗑️ ボタンでいつでも全消去できます
- **別タブ / 別デバイスへの共有**: 行われません (= 翌日別のデバイスで同じ質問をしても「過去の会話」は引き継がれません)
- **自社 DB への保存**: ありません (DB 容量や課金には一切影響しません)
- これは V1 の意図的設計 (シンプル + プライバシー優先 + DB コスト最適化)

### Q6. 結果カードをクリックしても権限エラーになる
**A.** 検索結果には自テナントの公開資産が並びますが、**詳細ページ側で別途権限チェック** があります。一部のリソース (例: メンバー限定のプロジェクト) では、メンバーでなければ詳細を見られない場合があります。検索で見えても詳細で 404 / 403 が出る場合は、所属プロジェクトのメンバー追加を管理者に依頼してください。

## 9. まとめ

| 用途 | クエリ例 |
|---|---|
| 過去の類似案件を探したい | 「金融系の基幹リプレースで予算超過した案件の対応」 |
| 似たリスクの対応事例を見たい | 「多重下請けで工数膨張した時の対策」 |
| ベテランのナレッジを引き出したい | 「PMBOK スコープ管理の実務的な工夫」 |
| 自分の過去メモを思い出したい | 「先月書いた KPI 関連の自分のメモ」 |
| 振り返りから学びを取り出したい | 「炎上案件の振り返りで挙がった改善事項」 |

「上位の数件で足りる」状態を作ることを目指して設計されています。**業務文脈を含めた自然文で質問する** ことで最大の効果が得られます。
