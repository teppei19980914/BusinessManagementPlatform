# Dogfooding 計画 (AI 補助なしでの機能実装によるドキュメント検証)

本ドキュメントは、人間駆動運用開始 (2026-06-01) 後に実施する **「AI 補助なしで 1 機能実装する」検証** の計画です。

> **目的**: 整備したドキュメント (リーディングパス / CONTRIBUTING / ADR / FEATURE_CATALOG / GLOSSARY / 各種運用 SOP) が、**AI の支援なしでも開発者 1 人で完結できる品質か** を実証する。
>
> 「ドキュメントを完璧にしてから運用する」より「実際に使って穴を発見する」方が圧倒的に ROI が高い。

---

## 1. 実施タイミング

### 1.1 推奨タイミング

**2026-06-15 ± 1 週間** (リリース後 2 週間目、緊急対応が落ち着いた頃)。

理由:
- リリース直後 1 週間は本物のインシデント対応に集中したい
- かといって 1 ヶ月以上待つと整備したドキュメントの記憶が薄れ、検証として弱くなる
- 2 週目なら自分の記憶もまだ新鮮で「ドキュメントだけで判断できるか」を真の意味でテストできる

### 1.2 検証時間

- 連続 4-8 時間 を 1 セッションとして 1-2 回 (合計約 1 営業日)
- AI を使わない縛りで小さな機能を 1 つ実装

## 2. 検証対象機能の選定基準

### Good candidate (検証として価値が高い)

- **マスタデータ追加系**: テーマ追加 / 言語追加 / 通貨追加等 — 横展開チェック (CONTRIBUTING §5.1) の実証になる
- **新規 page.tsx + route.ts 1 セット**: E2E カバレッジゲート (pnpm e2e:coverage-check) の動作実証
- **既存サービスへの新規メソッド追加**: 認可・テナント境界 (CONTRIBUTING §5.2) の実証

### Bad candidate (検証として価値が低い)

- **核心機能の改修**: 提案エンジン / 課金ロジックは複雑すぎて 1 セッションで完結しない
- **純粋な docs 修正**: コード変更ゼロでは開発フロー全体の検証にならない
- **既存テストの修正のみ**: 新規機能設計の判断プロセスを検証できない

### 推奨候補 (例)

1. **「お気に入りプロジェクト」機能の追加** (規模感: 小〜中)
   - 新規 `User.favoriteProjectIds` JSONB カラム + migration
   - サービス層 `addFavorite` / `removeFavorite` / `listFavorites`
   - 一覧画面に ⭐ アイコン
   - 単体テスト 3-5 件 + E2E テスト 1 件
2. **タグの編集権限拡張** (規模感: 小)
   - 現状 PM のみ編集可能なタグを TL も編集可能にする
   - 権限マトリクス (PERMISSION_MATRIX.md) の更新
   - サービス層の認可チェック改修
   - 単体テスト 2-3 件
3. **メモのカテゴリ機能** (規模感: 中)
   - Memo に `category` enum カラム追加
   - フィルタ機能を一覧画面に追加
   - 新規 page.tsx (カテゴリ別ビュー) + route.ts (フィルタ API)

## 3. 検証プロトコル (ルール)

### 3.1 禁止事項

- **Claude Code / ChatGPT / Copilot 等の AI ツール一切使用禁止**
  - IDE の標準的なコード補完 (TS LSP) は OK
- **AI が書いた docs / 既存コードの参照は OK**
  - 整備したドキュメント類は読んでよい (むしろ読まないと検証にならない)
- **同僚 / コミュニティへの質問は OK だが記録する**
  - 「docs だけで判断できなかった」箇所として後で穴の特定に使う

### 3.2 必須記録事項

検証中、以下を `docs/operations/dogfooding-logs/2026-MM-DD-<feature>.md` に時系列で記録:

```markdown
# Dogfooding ログ: <機能名> (YYYY-MM-DD)

- 検証時間: HH:MM 〜 HH:MM (合計 〇分)
- 検証者: teppei
- 対象機能: <概要>

## タイムライン

### 0:00 着手前
- 読んだドキュメント: docs/README.md → リーディングパス Day 1
- 期待: 〇〇から始めるはず

### 0:15 環境構築
- 参照: docs/operations/SETUP_LOCAL.md
- 詰まり: ...
- 解決: ...

### 0:45 設計判断
- 参照: docs/business/FEATURE_CATALOG.md でカテゴリ判定
- 参照: 関連 ADR
- 判断: ...

### 1:30 実装
- 参照: src/services/... の既存パターン
- 詰まり: ...

### 3:00 テスト
- 単体テスト追加
- pnpm test 通過
- pnpm e2e:coverage-check で gap 検知 ← OR not?

### 4:00 PR 作成
- 参照: CONTRIBUTING.md PR テンプレート
- §5 コードレビューチェックリストを 1 つずつ確認

## 発見した穴

| # | ドキュメント | 問題 | 改善案 |
|---|---|---|---|
| 1 | docs/operations/SETUP_LOCAL.md | xxx の手順が古い | yyy に修正 |
| 2 | CONTRIBUTING.md §5.2 | テナント境界の説明が抽象的 | 具体例を追加 |

## Action Items

- [ ] <発見した穴の修正 PR を起票>
- [ ] <足りないドキュメントを新設>
```

### 3.3 評価指標

検証完了後、以下を自己評価:

| 指標 | 目標値 | 計測方法 |
|---|---|---|
| ドキュメントだけで完結した割合 | >80% | 「外部 Q&A サイト / AI / 同僚」で解決した割合の逆 |
| 詰まりの総時間 | <30% | 「進めなくて立ち止まった時間」/ 総時間 |
| ドキュメントの穴の発見数 | 5-15 件 (理想) | 0 件 = ドキュメントが完璧 or 検証が浅い、20件超 = ドキュメント全面見直し必要 |
| 新規機能の品質 | テスト全通過 + 動作確認済 | CI 結果 |

## 4. 検証後のアクション

### 4.1 発見した穴の処理

各穴を Issue 化し、優先度を付ける:

- **Critical (実装ブロッカーになった)**: 即時修正、別 PR で対応
- **Major (時間ロスを生んだ)**: 1 週間以内に対応
- **Minor (気になっただけ)**: バックログで対応

### 4.2 ドキュメント追加・更新

優先度の高い穴を埋める PR を起票。
特に以下のドキュメントを更新候補に検討:

- リーディングパス (docs/README.md): 順序や深さの調整
- CONTRIBUTING.md §5: 実体験ベースのチェック項目追加
- 各 ADR の Consequences / Risk セクション: 実装時に気づいた落とし穴
- docs/knowledge/KDD_PATTERNS.md: 新規 KDD エントリ追加

### 4.3 次回検証の計画

- 3 ヶ月後 (2026-09 頃) に再度 Dogfooding 実施 (改善効果の検証)
- メンバー増員時は、新メンバーに同じプロトコルで実施してもらう (オンボーディング体験そのものの検証)

---

## 5. メンバー追加時の応用

将来メンバーが増えた場合、新メンバーの **最初の 1-2 週間** で本プロトコルを応用:

- 新メンバーは AI を使わずにオンボーディング (整備した docs だけで開発できるか)
- teppei (既存メンバー) は **質問されたら答えるが、自分から教えない**
- 新メンバーの「詰まりログ」が最も価値の高いドキュメント改善源
