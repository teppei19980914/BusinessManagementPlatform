# 顧客フィードバック トリアージプロセス

本ドキュメントは、外部公開後 (2026-06-01〜) に受領する顧客フィードバック (要望・不具合報告・質問) を **見落とさず・公平に・継続的に** 処理するためのプロセスを定義します。

> **背景**: 1 人運用 (teppei) では FB が複数チャネルから散発的に届くと埋もれやすい。
> 仕組み化しないと「重要度の高い指摘を見落とす」「同じ要望を別案件として 2 度起票する」等の事故が起きる。

---

## 1. FB の受領チャネル

| # | チャネル | 用途 | 想定量 |
|---|---|---|---|
| 1 | サポートメール (`support@<domain>`) | 不具合報告 / 一般質問 | 月数件〜数十件 |
| 2 | Discord (将来) | カジュアル要望 / 質問 / コミュニティ議論 | 月数十件〜数百件 |
| 3 | 直接連絡 (LinkedIn / X / 知人経由) | 営業相談 / 初期ヒアリング | 月数件 |
| 4 | アプリ内フィードバックフォーム (将来) | 画面ごとの即時報告 | 月数件 |
| 5 | 自身の dogfooding (内部利用) | 自分が使って気づいた改善点 | 月数件〜十数件 |
| 6 | エラー集約 (`system_error_logs`) | 自動収集される異常 | 日次レビュー |

---

## 2. 集約方針

すべての FB を **GitHub Issues** に集約する。
チャネル別に別管理するとサイロ化するため、最初の窓口は分散していても **最終的に 1 つの triage 場所** に流す。

### Issue ラベル設計

| カテゴリ | ラベル | 説明 |
|---|---|---|
| 種別 | `bug` / `feature-request` / `question` / `improvement` / `security` | 何の種類か |
| 起源 | `from:support-email` / `from:discord` / `from:direct` / `from:dogfooding` / `from:error-log` | どこから来たか |
| 重要度 | `priority:p0-critical` / `p1-high` / `p2-medium` / `p3-low` | §3 のマトリクスで判定 |
| 状態 | `triage` (未判定) / `accepted` / `wont-fix` / `duplicate` / `in-progress` | 進行状態 |
| カテゴリ | `cat:project` / `cat:knowledge` / `cat:billing` / `cat:auth` / `cat:suggestion-engine` / `cat:admin` / `cat:other` | [FEATURE_CATALOG.md](../../business/FEATURE_CATALOG.md) と整合 |

---

## 3. 重要度判定マトリクス

| 影響 \ 緊急度 | 即時 | 数日 | 数週 | いつでも |
|---|---|---|---|---|
| **全テナント機能停止 / データ漏洩** | P0 | P0 | — | — |
| **特定テナント機能停止 / 経済的損失** | P0 | P1 | — | — |
| **業務に支障 (回避策あり)** | P1 | P1 | P2 | — |
| **改善要望 / 軽微な UI ズレ** | — | P2 | P2 | P3 |
| **質問 / 情報共有** | — | — | P3 | P3 |

### 各 P レベルの SLA

| P レベル | 一次回答 | 一次対応開始 | 完全解決目標 |
|---|---|---|---|
| **P0 critical** | 1 時間以内 | 即時 | 24 時間以内 |
| **P1 high** | 24 時間以内 | 3 営業日以内 | 2 週間以内 |
| **P2 medium** | 5 営業日以内 | 適宜 | 次マイルストーン |
| **P3 low** | 10 営業日以内 | バックログ管理 | 半年〜未定 |

> **1 人運用での現実的目標**: 平日 = 上記準拠、休日 = P0 のみ対応、P1 以下は翌平日。
> ユーザに対しても「平日 9-18 時対応」と明示しておく。

---

## 4. 日次トリアージルーチン

### 平日朝 (9:00-9:30) の 30 分

1. **新規 Issue / メール / Discord 確認** (10 分)
   - 各チャネルを順次チェック
   - 重複は元 Issue にリンクして閉じる
2. **未トリアージ Issue にラベル付与** (15 分)
   - 種別 / 起源 / カテゴリのラベルを必須付与
   - 重要度を判定 (§3 マトリクスを使用)
   - 必要なら追加情報を要求 (`question-from-developer` ラベル + コメント)
3. **P0 / P1 への即時対応判断** (5 分)
   - P0: 当日中に手を動かす
   - P1: 今週中の作業計画に組み込み

### 週次 (金曜午後 1 時間)

1. **未対応 Issue の棚卸し**
   - 1 週間以上 `triage` ラベルのままの Issue を再判定
   - 「待ち」状態の Issue (ユーザ返信待ち等) を再確認、必要なら催促または close
2. **P2 / P3 のバックログ整理**
   - 同種の要望をまとめて 1 Issue にエポック化
   - 次マイルストーン候補を仮選定
3. **指標確認**
   - 今週の新規 Issue 数 / 解決数 / 中央値リードタイム
   - P0/P1 の累積数推移

### 月次 (月末)

1. **Action Items の振り返り**
   - 完了済 Issue を post-mortem 観点で見直し
   - 何度も同じ種類の Issue が来ていれば、UI 改善 / ドキュメント補強で予防
2. **ロードマップ反映**
   - P2/P3 で蓄積している要望のうち、頻度・重要度の高いものを次四半期計画に組み込む

## 5. Issue テンプレート

`.github/ISSUE_TEMPLATE/` に以下のテンプレートを用意する (まだ未整備、本ドキュメントの参考):

### A. バグ報告

```markdown
---
name: Bug Report
about: 不具合を報告
labels: bug, triage
---

## 概要
<何が起きたか 1-2 行>

## 再現手順
1. ...
2. ...

## 期待する動作
<何が起きるべきか>

## 実際の動作
<実際に起きたこと、エラーメッセージ等>

## 環境
- ブラウザ:
- OS:
- アカウント (差し支えなければ): tenant ID / user role

## スクリーンショット / ログ
<あれば添付>
```

### B. 機能要望

```markdown
---
name: Feature Request
about: 新機能・改善の要望
labels: feature-request, triage
---

## 解決したい課題
<どんなユースケースで困っているか>

## 期待する解決策
<具体的にどう動いてほしいか。なければ「アイデアなし、議論したい」と書く>

## 代替案 / 現状の回避策
<今はどう対処しているか>

## 補足情報
<関連リンク、参考になる他サービスの実例等>
```

### C. 質問

```markdown
---
name: Question
about: 使い方や仕様についての質問
labels: question, triage
---

## 質問内容
<何を知りたいか>

## 関連する画面・機能
<どこを見ていて疑問が出たか>

## 自分で調べたこと
<docs / ヘルプ / 過去 Issue で確認したこと>
```

## 6. ユーザ向け回答テンプレート

### A. 一次回答 (受領確認)

> 件名: 【たすきば Knowledge Relay】お問い合わせを受け付けました
>
> 〇〇様
>
> お問い合わせいただきありがとうございます。内容を確認し、以下の通り対応を進めます。
>
> - 受付番号: #XXX (GitHub Issue)
> - 種別: バグ / 要望 / 質問
> - 想定対応時期: P0 24h / P1 2週間 / P2 次マイルストーン / P3 バックログ
>
> 追加の情報が必要な場合は別途お伺いします。
> 進捗があり次第ご連絡いたします。

### B. 解決時の回答

> 件名: 【たすきば Knowledge Relay】#XXX 対応完了のお知らせ
>
> 〇〇様
>
> ご報告いただいた件 #XXX について対応が完了しました。
>
> - 修正内容: <簡潔に>
> - リリース日時: YYYY-MM-DD HH:MM
> - 確認方法: <該当機能の確認手順>
>
> ご報告ありがとうございました。引き続きよろしくお願いします。

### C. 対応保留・代替案提示

> 件名: 【たすきば Knowledge Relay】#XXX へのご返信
>
> 〇〇様
>
> ご要望いただいた件 #XXX について、以下の判断とさせてください。
>
> - 判断: 現時点では対応見送り (理由: <設計方針 / 優先度 / 技術的制約>)
> - 代替案: <現在の機能でどう実現できるか、あれば>
> - 今後の方針: <将来の検討タイミング>
>
> 別のご相談やご意見はいつでもお待ちしています。

## 7. ベンチマーク指標 (月次レビュー)

| 指標 | 目標 (1 人運用) | 計測方法 |
|---|---|---|
| 新規 Issue 受領数 | 月 0〜50 件 (テナント数に応じてスケール) | GitHub Issue created |
| 一次回答リードタイム (P0/P1) | P0: <1h, P1: <24h | Issue created → first comment |
| 解決リードタイム (P1) | <2 週間 | Issue created → closed |
| トリアージ未済滞留 | <5 件 | `triage` ラベル付き Issue 数 |
| 重複 Issue 率 | <10% | `duplicate` クローズ率 |

## 8. エスカレーション (チーム拡大時)

将来メンバーが増えた場合の役割分担方針 (現時点では teppei 1 人):

| 役割 | 担当 |
|---|---|
| 初期トリアージ (全 Issue にラベル付与) | チーム輪番 (週交代) |
| P0 対応 | オンコール担当 (週交代) |
| カテゴリ別深掘り対応 | 該当機能領域の担当者 |
| 月次レビュー | プロダクトリード |
