# チャットボット意味検索機能 — 機能仕様 (Specification)

本ドキュメントは、ユーザが自然文で「過去資産を探す」目的のためのチャットボット意味検索機能の機能仕様書。サービスの哲学 ([about.md §3-2 / §5-2](../public/about.md)) と整合するよう、**「上位の数件で足りる」意味検索を、ユーザの能動的問い合わせから引き出す** 経路として設計する。

技術的な実装設計は (実装着手時に [../design/CHAT_SEMANTIC_SEARCH.md](../design/CHAT_SEMANTIC_SEARCH.md) を新規作成予定)、課金モデルの全体像は [../business/TENANT_AND_BILLING.md](../business/TENANT_AND_BILLING.md)、既存提案機能との位置関係は [./SUGGESTION_FEATURE.md](./SUGGESTION_FEATURE.md) を参照。

---

## 1. チャットボット意味検索機能とは何か

「**ユーザが自然文で『こういう状況の過去資産がほしい』と入力すると、システムが意味検索で 5 種類の資産を横断的に取得し、スコア順で提案する**」機能。既存の[提案機能](./SUGGESTION_FEATURE.md)が「**システムから能動的に届く**」経路を担うのに対し、本機能は「**ユーザが自発的に探したい瞬間**」の経路を担う。両者は同じ意味検索基盤 (Voyage embedding + pgvector Cosine 類似度) を共有する。

### 1.1 サービス哲学との位置づけ

| 観点 | 既存提案機能 | 本機能 (チャット意味検索) |
|---|---|---|
| 発動契機 | システム自動 (Project 作成・参考タブ等) | ユーザ自発 (チャット入力) |
| クエリ | Project の `purpose + background + scope` | 自然文 (ユーザ入力テキスト) |
| 対象資産 | Knowledge / 過去 Issue / 過去 Risk / Retrospective (4 種) | Project / Knowledge / RiskIssue / Retrospective / Memo (**5 種**) |
| プレゼン | カード一覧 (3 軸合成スコア) | カード一覧 (意味類似度メイン) |
| 哲学整合 | §5-1 能動的提案 | §3-2 / §5-2 「数件で足りる意味検索」 |

### 1.2 機能スコープ (V1)

- **Level 1 のみ実装**: 意味検索 → 結果カード表示。LLM による要約・回答生成は **行わない** (将来の Pro プラン差別化価値として温存)。
- 会話履歴は **永続化しない** (Client State のみ、リロードで消去)。
- 種別フィルタ UI は **出さない** (5 資産デフォルト全網羅、カードに種別バッジで識別)。

## 2. API 呼び出しトリガー (誰がいつ何を呼ぶか)

| # | トリガー | 呼び出される API | 1 操作あたり呼び出し回数 |
|---|---|---|---|
| **①** | **ユーザがチャット送信** (Enter / 送信ボタン) | **Voyage** (クエリ側 embedding 生成) | Voyage **1 回** |
| **②** | **検索結果の取得** | **Supabase pgvector のみ** (5 テーブル横断 SELECT) | **外部 API 呼び出しなし (¥0)** |
| **③** | **結果カードのクリック** (詳細遷移) | なし | なし |

### 2.1 設計上の重要点: 検索結果取得は ¥0

トリガー②は **既存 embedding を使った類似度計算のみ**で完結する。チャット 1 回あたりの追加 API コストは **トリガー① の Voyage 1 回のみ** ([§5 コスト試算](#5-コスト試算) 参照)。

### 2.2 提案機能との比較 (課金トリガー)

| 項目 | 提案機能 | チャット意味検索 |
|---|---|---|
| トリガー回数 | エンティティ作成・更新時 (書込操作) | チャット送信時 (読込操作) |
| 課金種別 (about.md§Q8 上の分類) | 1 操作 = 1 API 呼び出し | **1 検索 = 1 API 呼び出し** (書込操作と同等に計上) |

→ 「読込操作だが API 呼び出し計上」という新しい挙動について、料金表 §Q8 への明示追記が必要。詳細は [§7 料金体系への影響](#7-料金体系への影響) 参照。

## 3. 機能仕様

### 3.1 アクセス経路・UI 配置

- **全ページ共通の右下フローティングボタン** (💬 アイコン)
- クリック → 右サイドパネル展開 (画面右側 1/3 をオーバーレイ)
- 認証済ユーザのみアクセス可 (NextAuth セッション必須)

### 3.2 チャット入力仕様

| 項目 | 仕様 |
|---|---|
| 入力欄 | 1 行〜複数行可、Enter で送信 / Shift+Enter で改行 |
| 文字数上限 | **8000 文字** (= `MAX_INPUT_CHARS`、これを超えた分は truncate 警告表示) |
| 最小文字数 | **制限なし (送信は常に可能)**。ただし **10 文字未満** の場合は送信ボタン下に注意文言 「⚠️ クエリが短いと検索精度が下がる可能性があります」 を表示し、ユーザに精度トレードオフを周知する (UX 低下を避けつつ、Voyage embedding の精度特性をユーザに伝える) |
| クライアント側 debounce | 1 秒 (連投スパム防止) |
| プレースホルダ例 | 「過去の似た案件で発生したリスクは?」 |

### 3.3 検索処理フロー

```
1. ユーザ送信
   ↓
2. クライアント → POST /api/chat/search { query }
   ↓
3. サーバ側:
   a. getAuthenticatedUser() で viewerTenantId / userId 取得
   b. レート制限チェック (LLM_RATE_LIMIT 流用)
   c. generateEmbedding({ text: query, inputType: 'query', featureUnit: 'chat-search-embedding' })
      └ Voyage 1 回呼出 + ApiCallLog 1 件記録
   d. 5 資産に対して searchSimilar() を並列実行 (Promise.all)
      └ tenantId フィルタ + seedDataEnabled 判定で MANAGEMENT_TENANT_ID も含めるか判断
      └ deletedAt IS NULL + content_embedding IS NOT NULL の行のみ
      └ visibility='public' のみ (draft 除外、既存ロジックと整合)
   e. 各資産で SUGGESTION_DEFAULT_LIMIT=50 件取得 → tier 分類 (strong/medium/weak)
   f. レスポンス組み立て (5 資産別 + tier 分類済)
   ↓
4. クライアント:
   - tier 順 (strong → medium → weak、weak は折りたたみ) で表示
   - 各カードに種別バッジ (📄Project / 📕Knowledge / ⚠️RiskIssue / 📋Retro / 📝Memo)
```

### 3.4 結果プレゼンテーション

既存提案機能と同じ tier 段階表示パターン:

| Tier | 表示 | カウント | 折りたたみ |
|---|---|---|---|
| **strong** | 「強く関連」セクション | 上位 30% | 展開 |
| **medium** | 「関連の可能性」セクション | 中段 50% | 展開 |
| **weak** | 「弱い関連性」セクション | 下位 20% | 折りたたみ (デフォルト) |

- **件数上限**: 各資産 `SUGGESTION_DEFAULT_LIMIT = 50` 件 = 5 資産合計最大 250 件 (weak 込み)
- **閾値**: `SUGGESTION_SCORE_THRESHOLD = 0.01` 以上 (PR-X6 で確定済、全網羅 + 段階表示の高再現率設計)
- **最低件数保証**: `SUGGESTION_MINIMUM_GUARANTEED_COUNT = 5` (シードと異業種でも 0 件にならない設計、既存ロジック流用)
- **tier 分類**: `assignPercentileTiers()` を 5 資産それぞれで適用 (既存ロジック流用、5 件以下は `classifyTier()` 絶対閾値方式にフォールバック)

カードクリック → 既存の各エンティティ詳細ページへ遷移 (権限チェックは詳細ページ側の既存ロジックに委譲)。

### 3.5 縮退モード時の挙動

`Tenant.monthlyApiCallCap` 超過時 ([about.md §Q8](../public/about.md) と整合):

1. クエリ側 Voyage 呼出が **`rate_limited` / `beginner_limit_exceeded` / `budget_exceeded`** を返す
2. クライアントに `{ degraded: true, reason: '...' }` を返す
3. UI に「💡 AI 機能は一時的に制限されています。テキスト類似度のみで検索します」表示
4. **pg_trgm fallback**: 既存 `computeTextSimilarities()` パターンを 5 資産に適用してテキスト類似度のみで検索結果を返す (タグは無関係なため、テキスト軸のみ単独使用)

これは既存 [`suggestRelatedIssuesForText`](../../src/services/suggestion.service.ts) の縮退設計と同じ思想。

### 3.6 認可・テナント境界

- **viewerTenantId 必須**: 検索結果は自テナント (+ `seedDataEnabled=true` ならシード `MANAGEMENT_TENANT_ID`) に限定
- 越境防止: メモリ memory ([feedback_tenant_isolation.md](../../../.claude/projects/c--Users-SF02512-GitHub-Private-BusinessManagementPlatform/memory/feedback_tenant_isolation.md)) と同方針、where 句に必ず `tenantId` を効かせる
- セキュリティ脅威モデルは [../security/SUGGESTION_ENGINE_THREAT_MODEL.md](../security/SUGGESTION_ENGINE_THREAT_MODEL.md) を流用 (本機能も同じ embedding 基盤のため同じ脅威モデルが適用)

### 3.7 レート制限

既存 `LLM_RATE_LIMIT` ([src/config/llm.ts](../../src/config/llm.ts)) をそのまま流用:
- 1 ユーザ / 1 分 10 回
- 1 ユーザ / 1 時間 60 回
- Beginner プラン: 月 100 回 (本機能と提案機能で **共有**、§4 参照)

## 4. プラン別挙動 (全プラン API 呼び出し計上)

本機能は **書込操作と同等に API 呼び出し 1 回として計上** する。プラン別の挙動は以下:

| プラン | チャット検索 1 回あたり | 月次上限 | 縮退時挙動 |
|---|---|---|---|
| **Beginner** | 月 100 回枠を **書込操作と共有** (1 検索 = 1 API 呼び出し) | 月 100 回 (書込含む) | pg_trgm fallback |
| **Expert** | **¥10 / 1 検索** (書込と同単価で従量課金) | 実質無制限 (テナント月次予算上限まで) | pg_trgm fallback |
| **Pro** | **¥30 / 1 検索** (書込と同単価で従量課金) | 実質無制限 (テナント月次予算上限まで) | pg_trgm fallback |

### 4.1 全プラン計上の根拠

- **サービス哲学の根幹**: about.md §5-2 が掲げる「**意味検索 = サービスの核心**」を成立させるため Voyage embedding は不可欠。これを使う限り、書込であれ読込であれ「**外部 AI を呼び出す = API 呼び出し 1 回**」という単位で統一的に計上することがユーザにとって最も透明性が高い。
- **Beginner の自己制御**: 月100回枠を書込と共有することで、「思いつきで連投」が自然に抑制される (= 書込余力を残すために慎重にクエリを練る経済圧力)。
- **Expert / Pro の透明な従量課金**: 1 検索 = 1 API 呼び出し = 書込と同単価。ユーザは「使った分だけ」のシンプルさを保持でき、テナント月次予算上限・予算消化率プログレスバー (about.md §Q2) でリアルタイムに費用を可視化できる。
- **運営コストとの整合**: Voyage 200M 無料枠を超過しても $0.02/M (¥2.5/M) なので運営持ち出しは最小、Expert 単価 ¥10/call との粗利は十分確保される (詳細は [§5 コスト試算](#5-コスト試算))。
- **Pro 単価 ¥30 の意味**: 現状チャット検索では Pro 固有の Sonnet 呼出は発生しないが、書込操作との価格整合性 + 将来の Level 2 (LLM 要約) で Sonnet 呼出を追加する余地を残す。

### 4.2 料金表 §Q8 改訂提案文言 (about.md 反映用)

> **課金対象（1 操作 = 1〜2 回カウント）**:
> - プロジェクトの新規作成・更新（自動タグ抽出 + ベクトル化）
> - ナレッジ・リスク・課題・振り返りの新規作成・更新（ベクトル化）
> - CSV / XLSX インポート（1 ファイルにつき 1 回）
> - 提案の説明文生成（**Pro プランのみ**、Sonnet による深い説明文）
> - **チャット意味検索の問い合わせ送信（全プラン共通、1 検索 = 1 API 呼び出しとして計上。書込操作と同単価）** ← 新規追加

→ 「読込操作だが意味検索のため Voyage 呼出が発生し、API 呼出として計上する」旨をテナント管理者ダッシュボードでも明示する (実装時に文言追加)。

## 5. コスト試算

### 5.1 単位コスト

| 項目 | 単価 | 備考 |
|---|---|---|
| Voyage クエリ embedding (運営側原価) | $0.02 / M token (Voyage 公式 [pricing](https://docs.voyageai.com/docs/pricing)) | 1 クエリ最大 8000 字 ≒ 12K token、無料枠超過分のみ |
| Voyage 無料枠 | 200M token / 月 | Organization 全体で共有 |
| Expert プラン売上単価 | ¥10 / 1 検索 | 書込と同単価、テナントへ課金 |
| Pro プラン売上単価 | ¥30 / 1 検索 | 書込と同単価、テナントへ課金 |
| Anthropic LLM 要約 (V1 未実装) | Sonnet ¥30/call | Level 2 で Pro 限定として将来追加 |

### 5.2 シナリオ A: リリース直後 (5-10 テナント / 月)

**前提**: 50 ユーザ × 月 10 回 = 500 クエリ (Expert プラン想定)

| 項目 | 月次使用量 | 月次運営コスト | 月次売上 |
|---|---|---|---|
| Voyage embedding (500 × 12K token) | 6M token | **¥0** (無料枠の 3%) | — |
| pgvector 検索 (5 資産 × 500 回) | 2,500 SELECT 文 | **¥0** (Supabase Free 内) | — |
| Expert テナント課金 (500 × ¥10) | — | — | **¥5,000** |
| **合計** | — | **¥0** | **¥5,000** |

→ **粗利率 100%** (運営コスト無料枠内)。

### 5.3 シナリオ B: 中規模 (50 テナント / 月)

**前提**: 500 ユーザ × 月 15 回 = 7,500 クエリ (Expert 80% / Pro 20% 想定)

| 項目 | 月次使用量 | 月次運営コスト | 月次売上 |
|---|---|---|---|
| Voyage embedding (7,500 × 12K) | 90M token | **¥0** (無料枠の 45%) | — |
| pgvector 検索 | 37,500 SELECT 文 | **¥0** (Supabase Pro 帯域内) | — |
| Expert テナント課金 (6,000 × ¥10) | — | — | ¥60,000 |
| Pro テナント課金 (1,500 × ¥30) | — | — | ¥45,000 |
| **合計** | — | **¥0** | **¥105,000** |

→ **粗利率 100%**。

### 5.4 シナリオ C: 拡大 (200 テナント / 月)

**前提**: 2,000 ユーザ × 月 20 回 = 40,000 クエリ (Expert 70% / Pro 30% 想定)

| 項目 | 月次使用量 | 月次運営コスト | 月次売上 |
|---|---|---|---|
| Voyage embedding (40,000 × 12K) | 480M token | **¥700** (超過 280M × ¥2.5/M) | — |
| pgvector 検索 | 200,000 SELECT 文 | **¥0** (Supabase Pro 帯域内) | — |
| Expert テナント課金 (28,000 × ¥10) | — | — | ¥280,000 |
| Pro テナント課金 (12,000 × ¥30) | — | — | ¥360,000 |
| **合計** | — | **¥700** | **¥640,000** |

→ **粗利率 99.9%** (運営原価率 0.11%)。書込操作 ([SUGGESTION_FEATURE.md §6.3](./SUGGESTION_FEATURE.md)) と同等の高粗利構造を維持。

### 5.5 監視ポイント

| 監視項目 | 閾値 | 超過時アクション |
|---|---|---|
| チャット由来 Voyage token 量 | Voyage 無料枠 (200M) の 70% (140M) | 警告メール、超過後は $0.02/M で運営持ち出し (粗利率には許容範囲) |
| クライアント連投 (1 ユーザ / 分 10 回) | LLM_RATE_LIMIT で自動制御 | HTTP 429 返却、UI 表示 |
| テナント月次予算上限到達 | テナント設定値 | チャット検索も書込操作と同様にブロック (= 縮退モード移行) |

## 7. 料金体系への影響

- **about.md §Q8 改訂**: §4.2 の文言提案を反映する PR を別途立てる (全プラン共通で「1 検索 = 1 API 呼び出し」を明示)
- **テナント管理者ダッシュボード**:
  - 全プラン: 「チャット意味検索も API 呼び出し 1 回として計上」明示
  - Beginner プラン: 月100回カウントに「書込操作 + チャット検索を含む」明示
  - Expert / Pro プラン: 予算消化率プログレスバー (about.md §Q2) にチャット検索分も自動加算 (`Tenant.currentMonthApiCallCount` / `currentMonthCostJpy` への加算は既存 `withMeteredLLM` 経由で自動実現)
- **Pro 単価 ¥30 の妥当性**: 現状チャット検索は Voyage embedding のみ (Sonnet 不使用) だが、書込との価格整合性 + 将来 Level 2 で Sonnet 呼出を Pro 限定追加する余地を残すため ¥30 で確定 (§4.1 参照)
